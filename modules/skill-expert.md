# 可选模块 M1：Skill / 专家搭配建议（默认关闭）

> **本模块默认不加载**，用户启用时才占用 token。
> 启用方式：把本文件内容追加到你的 `AGENTS.md` / `CLAUDE.md`，或在其中 `@modules/skill-expert.md` 引用。

## 一、要不要先找现成 Skill

不要默认去找。先过三道过滤：

1. **有没有成熟标准流程？**
   部署、安全审计、数据库迁移、组件生成、文档生成 → 有现成 skill 的概率高
2. **是垂直领域，还是本项目特有逻辑？**
   垂直领域 → 值得找；与本项目强耦合的一次性逻辑 → 别找，直接写更快
3. **会重复出现吗？预计耗时 > 30 分钟吗？**
   会重复 且 > 30min → 找 skill 划算
   一次性 或 < 10min → **找 skill 的时间比直接做完还长**

**核心判据**：找 skill 本身要花时间和 token。任务越小，找 skill 越不划算。

## 二、识别「伪 Skill」

市面上不少所谓 Skill 只是一堆方法论文字 —— 读完仍然不知道下一步该干什么。

| | 特征 |
| --- | --- |
| **真 Skill** | 有具体操作步骤、命令、检查清单、可运行脚本 |
| **伪 Skill** | 只有原则、心法、注意事项 |

**伪 Skill 不是没价值，但它不省时间** —— 当参考资料读，别当工具用。

一条实用判断：如果把它删掉，你的做法会不会变？不会 → 它就是伪 Skill。

## 三、要不要上专家 / 角色

抽象判据：当你需要的不只是「把事做完」，而是「从某个视角审视这件事」，就该引入角色。

- **单一视角** → 一个角色足够。例：写文档，只配 writer。
- **多视角对抗** → 需要角色组合。例：重构核心模块 = 实现 + 质量 + 风险三个视角。

**经典三角**

| 角色 | 职责 | 何时需要 |
| --- | --- | --- |
| Builder | 把东西做出来 | 几乎总是 |
| Reviewer | 质量、一致性、可维护性 | 代码需要长期维护 |
| Auditor | 安全、性能、合规风险 | 涉及数据 / 资金 / 对外服务 |

**判据**：L1 打分表里「出错代价」得分越高，越该补 Auditor。

## 四、跨工具对照

同一件事在不同工具里的名字：

| 概念 | WorkBuddy | Claude Code | Cursor | Codex |
| --- | --- | --- | --- | --- |
| 可复用能力包 | Skill | Skill / slash command | Rule | 无原生机制 |
| 角色 / 子代理 | 专家 / 专家团 | subagent | 用 rule 模拟 | agent |
| 常驻项目规则 | 工作区记忆 | CLAUDE.md | .cursorrules | AGENTS.md |

## 五、行为准则

- 建议要**具体**：说「补一个 Auditor 做安全审查」，而不是「可以考虑专家团」。
- 只在**明显值得**时才说。拿不准就别说。
- 仍然遵守 L0 约束：一行说完、不中断、每会话最多一次。
